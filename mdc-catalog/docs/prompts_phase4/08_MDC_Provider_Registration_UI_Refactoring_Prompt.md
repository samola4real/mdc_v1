## 2. Registration UI lock

One form, three primary sections, existing two mode buttons and existing advanced payload preview collapsed. No wizard, no separate Additional offering information panel.

1. Provider information: name, ID, country, company description; existing controlled certification multi-select; optional repeatable Other certifications with duplicate prevention.
2. Offering information: name, ID, part family dropdown, auto-derived read-only category, support status (existing contract values; Confirmed default). Optional collapsed Additional service details: Production mode (describes production repetition/volume, not company size), Industries served, Other service information. Preserve flexible custom offering map, including an optional custom name/value entry mechanism inside this subsection rather than standalone panel; avoid duplicate or reserved keys. Do not mandate extra details.
3. Capability information: before family selected show concise prompt. After selecting family show supported part-type multi-select (empty on initial registration), family/part-specific specifications, materials and grades, processes, general capabilities, collapsed optional additional technical capabilities. Use actual catalogue filters for controlled options; never hardcode a provider or add unsupported controlled values. Retain existing standard-specific fields and supported units.

### Conditional rendering and draft isolation
- Gear -> precision_gears: spur, helical, bevel, worm, crown from live filters; shared gear module min/max, outside diameter min/max, DIN/ISO/AGMA quality standard and class (existing contract semantics).
- Shaft -> precision_shafts: plain, stepped, splined, worm, hollow from filters; family length max and outer diameter min/max; spline module only for selected eligible splined shaft.
- Metal part -> precision_metal_parts: block, plate, bracket, bushing, roller, collar from filters. Each selected box type has its own max length/width/height; each selected round type has its own max outer diameter. Tolerance and surface finish remain existing custom capability fields. Selecting multiple types never hides another selected type's dimensions or reassigns its values. Do not invent new capability fields. Store dimensions keyed by type. Removing a type excludes its data from outgoing payload; reselecting before submission can restore only its own draft. Family change warns before discarding populated family-specific information; never leak hidden family-specific values (including metal tolerance/finish) into a different family. Shared entries remain visible for provider review. 
- Preserve existing eligibility rules for confirmed part-specific capabilities. In registration, newly selected types inherit offering support status; explain that unconfirmed types cannot publish confirmed type-specific measurements. Disable ineligible controls with clear explanation, warn before status change that would omit entered data; retain isolated draft if appropriate, never silently publish as confirmed. Do not introduce per-type status editing in this task.
- Materials: live controlled multi-select, one independent editable comma-separated grade input per selected family (grades are free text). Keep grades keyed by material; removal/reselection must not clear surviving or unrelated grades. Custom material families with independent free-text grades are separate provider-declared entries. No controlled codes for unknowns. Trim/deduplicate ordinary inputs, avoid destructive normalization of meaningful stored values.
- Processes: live controlled multi-select plus optional Other manufacturing processes. No machine-specific capacities, routing, process-specific batch/lead times or scheduling. Batch size means supported customer order quantity for the offering; lead time is declared offering-level delivery range. Use existing Tasowheel reference only: precision gears, 100–2000 pieces, 8–12 weeks; machining/hobbing/heat treatment/hard turning/tooth grinding in separate DTD use case is context, not a routing encoded by MDC. Do not seed illustrative data into a blank form.
- General capability fields retain current canonical bounds and units; optional technical entries parameter/value/unit/notes. Prevent duplicate names, dedicated-field collisions and collisions with extension keys; no last-write-wins. Blank incomplete custom rows need actionable feedback rather than silent omission when meaningful input exists.

## 4. Locked user-facing response behavior

- Required fields, ID format/prefix and provider-offering ID relationship are explained inline; retain IDs immutable after creation. Clear field feedback for missing/invalid fields, range inversions and invalid values according to current contract. No new mandatory technical fields unsupported by contract.
- Loading catalogue: show loading state, clear error and retry option if fetch fails. No invalid dropdown defaults. Keep unrelated inputs intact.
- Validate publication: non-mutating POST /api/provider-publication/validation. Busy state, prevent double submission. Show domain result, not transport-only success: only explicit valid:true is success ("Validation successful. Your information is ready to register."). Invalid result -> "Please correct the highlighted information." Display available backend messages and map to relevant controls where possible, raw details collapsed. No successful status inferred from HTTP 200 alone. Any payload change invalidates prior validation; show "Information changed. Validate again before registering." Registration requires current successful validation (frontend-only UX gate, no API contract change). If this is incompatible with actual response semantics, report before implementing.
- Register provider: POST /api/provider-publication once, with current validated payload. Show progress, lock concurrent actions. Confirm only verified accepted response, display provider/offering identity and publication receipt. In current Stage 1 Preview, accepted with sync_pending/pending -> "Provider registered successfully. Manufacturing information has been saved." plus "Semantic synchronization pending. Search availability is not yet confirmed." Do not claim immediate discovery. If receipt genuinely reports completed, report exact status; do not independently claim search availability without evidence.
- Validation failure, duplicate ID (409) or other definite rejected request: preserve draft, actionable explanation, enable corrective edits; no blind retry.
- Timeout, uncertain network failure or post-commit 503: show "Registration outcome could not be confirmed. Check the provider before trying again." Preserve draft and use existing safe read-back GETs to distinguish already-created vs absent vs still uncertain; never auto-repeat POST or falsely claim failure/success. Preserve publication ID when available.
- After confirmed successful registration, retain existing transition to Update Existing Provider/read-back of submitted provider and offering; if read-back fails, distinguish accepted publication from read-back failure, preserve receipt, provide Load provider guidance. Do not silently select another offering or overwrite identity. No update UI redesign.
- Protect nonempty registration draft on mode change; prompt discard/cancel, clicking already active mode should not reset. Retain advanced JSON/response details collapsed. No raw credentials, tokens or internal stack traces in UI/report.
