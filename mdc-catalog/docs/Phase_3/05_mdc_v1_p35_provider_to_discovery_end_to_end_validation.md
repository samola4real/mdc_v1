## Validation strategy

P3.5 first proves the P3.4 provider is absent from the current Fuseki graph and deployed discovery response. It then processes the pending outbox through the trusted local synchronization command and proves the same provider appears in Fuseki and deployed canonical search.

## Synchronization policy

Vercel Production must remain:

```text
MDC_CATALOG_SYNC_ENABLED=False
```

The trusted local operator environment may temporarily set:

```text
MDC_CATALOG_SYNC_ENABLED=True
```

only for:

```text
python backend/manage.py sync_service_discovery_catalogue
```

The setting must be removed from the local process afterwards.

No new public synchronization endpoint is introduced.

## Remote query path

The deployed Vercel runtime must have a live remotely reachable `SERVICE_DISCOVERY_FUSEKI_QUERY_ENDPOINT`. The temporary Cloudflare Quick Tunnel used in P3.3 may be reused while it remains live. If the tunnel hostname has changed, update only the Vercel Production query endpoint and redeploy. Do not expose/configure Graph Store write credentials in Vercel.

## P3.5 acceptance

P3.5 is complete when:

- pre-sync verification proves the P3.4 provider is absent from Fuseki and deployed canonical discovery;
- the real pending P3.4 outbox is processed through the existing Graph Store synchronization path;
- PostgreSQL publication/outbox records become synchronized/succeeded with no error;
- direct Fuseki SPARQL contains `p34_api_validation_provider` and its controlled metal-parts offering;
- deployed `POST /api/service-discovery/search` returns `p34_api_validation_provider`;
- public contract remains `contract_version=1.0` with no `/api/v1` route;
- PostgreSQL remains the operational source of truth;
- Vercel-side synchronization remains disabled;
- no secrets are printed or committed.
