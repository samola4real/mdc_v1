# M3 — Complete lifecycle: permanent deletion and attribute removal (Codex task prompt)

**Milestone:** M3 only. **Repository:** `samola4real/mdc_v1`. **Project root:** `mdc-catalog/`.
**Prerequisite:** M2 merged to `origin/main` (reviewed merge commit `12aa650689a1976c8cfe7a950cd40016cba08d2e`). Read `docs/codex/current_refractor _plan.md` only as milestone context; current source and tests are the implementation authority.

## Required final behavior

Implement the accepted backend lifecycle contract, without touching the demo frontend:

- `DELETE /api/providers/{provider_id}`: **permanently** remove one provider, its offerings, certifications, capabilities and other dependent **operational** rows; unrelated providers and their offerings are unchanged.
- `DELETE /api/offerings/{offering_id}`: **permanently** remove only that offering and its own capabilities, preserving the parent provider and every sibling, including same-category siblings introduced in M2.
- Remove an individual editable provider/offering attribute using the existing `PATCH` endpoint, with a **documented, unambiguous removal contract** that preserves unrelated attributes. Avoid a new field-specific DELETE endpoint. Do not allow removing required identity/category/family attributes.
- Both DELETE operations are ordinary lifecycle writes under the **existing** publication enable flag, temporary pilot authentication opt-in and secured-mode policy, plus the **existing independent ETag/If-Match precondition machinery**. Preserve `X-MDC-If-Match` compatibility and response conventions. No new token/JWT requirement.
- Record durable deletion **outbox events** and sufficient minimal publication evidence transactionally so M4 can update the RDF/Fuseki catalogue later. Existing `CatalogueSyncEvent.Operation.DELETE` already exists; inspect actual schema before adding migrations. A successful M3 DB deletion is **not** yet a claim of immediate semantic publication: M4 will implement automatic synchronization and search visibility.

## Deletion design and implementation

4. Define one precise, documented response policy before coding: use current revision ETag preconditions for DELETE (require the current ETag even if temporary pilot authentication is disabled); `428` missing, `412` stale, `400` malformed, `404` missing/repeated DELETE, gated writes consistent with existing behavior; an accepted DB deletion should return a clear JSON lifecycle receipt (recommended `200`) including `contract_version`, `operation: "delete"`, target entity/id, `publication_id` and **pending** semantic synchronization status. Do not return `204` with a body or misleading `synchronized` status. Document exact response/error semantics.
5. Implement transactionally: lock target/related rows as appropriate, check ETag before mutation, take needed identifier snapshots, create a deletion publication record and `DELETE` outbox events **before** deleting operational rows, then delete exactly the target rows. For provider deletion, ensure surviving `ProviderPublication` records are not unintentionally deleted via FK cascade; for offering deletion do not affect siblings. Preserve sufficient tombstone metadata (entity IDs, operation, ordering/revision as necessary) for M4 to process the removal even though the operational rows no longer exist. Examine whether existing `ProviderPublication.Operation` choices need to include `DELETE` and create only necessary, safe migrations.
6. Define a minimal explicit retention policy in the implementation report: permanent deletion must clear provider/offering **operational data**, and historical publication payloads/snapshots must not inadvertently retain the full deleted provider's identifying/capability data merely through `on_delete=SET_NULL`. Retain only the minimal non-sensitive tombstone/audit/outbox metadata necessary for durable sync and debugging, or clearly document and implement an alternative bounded retention policy consistent with irreversible deletion. No blanket cascade removing pending deletion events. Never hard-delete unrelated provider history.
7. For provider DELETE, generate semantically sufficient provider and offering delete events or one explicit provider-deletion event that a full catalogue rebuild can deterministically act upon; document why. For offering DELETE, generate only relevant offering deletion event(s), touch the surviving parent provider revision to invalidate stale aggregate ETags, and keep sibling identities/capabilities unchanged. If a provider has zero offerings, provider deletion must still work.
8. Review current `PATCH` behavior: `OfferingPatchSerializer` supplies full JSON maps for selected capability containers and the write service replaces those containers, while omitted top-level fields remain unchanged. Choose and document an easy unambiguous field-removal contract (e.g. GET current offering and ETag, PATCH a complete updated selected map with exactly one optional key removed). If an additional explicit clearing operation is needed for editable scalar or provider custom fields, implement narrowly with validation and tests; **do not** introduce ambiguous null/absent semantics or silently replace sibling attributes. Clearly distinguish removed/not-declared versus an explicit unknown value, and keep valid provenance, numeric constraints and forbidden route/secret-key validation. PATCH must not modify immutable IDs or controlled offering category/family.
9. Keep the M1 no-auth option reversible: with `MDC_PROVIDER_LIFECYCLE_AUTH_REQUIRED=False` and actor flag false, DELETE and PATCH work without auth/actor headers in the dedicated test profile; when true, original bearer and actor checks still apply. ETag protection remains independent in both modes.
