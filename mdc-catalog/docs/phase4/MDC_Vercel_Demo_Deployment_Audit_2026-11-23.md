## 5. Authentication and Authorization Findings

**VERIFIED** `MDC_PROVIDER_LIFECYCLE_AUTH_REQUIRED` controls the Django Bearer gate for lifecycle reads, validation, and writes. `MDC_PROVIDER_LIFECYCLE_SERVICE_TOKEN` supplies the token for that gate. `authenticate_lifecycle_request` challenges a missing or invalid Bearer token with `401` when auth is required. With auth required and an empty configured token it returns `503 trusted_lifecycle_auth_unavailable`. [Deployed lifecycle security helper](https://github.com/samola4real/mdc_v1/blob/b9275258bf4a2455814ad9b2af9621e0a5d01327/mdc-catalog/backend/apps/api/lifecycle_security.py)

**VERIFIED** The Production project has an explicit, sensitive auth flag entry that predates the serving deployment. It also has explicit token, write actor, and concurrency entries. The code defaults auth, actor, and concurrency to `True` in `config.settings_production`. Live `401` establishes effective auth and implies a nonempty configured token in the running application. **INFERRED** The build uses the explicit Production auth setting given its presence before build and the documented enabled profile. API metadata did not expose the raw flag value or per-deployment environment snapshot. [Deployed Production settings](https://github.com/samola4real/mdc_v1/blob/b9275258bf4a2455814ad9b2af9621e0a5d01327/mdc-catalog/backend/config/settings_production.py) · [P3.2 configuration history](../Phase_3/02_mdc_v1_p32_trusted_lifecycle_pilot_enablement.md)


| Lifecycle environment entries | Project metadata | Effective Production behavior |
| --- | --- | --- |
| `MDC_PROVIDER_LIFECYCLE_AUTH_REQUIRED` | **VERIFIED** Production sensitive, Preview encrypted | **VERIFIED** Required for the probed routes. |
| `MDC_PROVIDER_LIFECYCLE_SERVICE_TOKEN` | **VERIFIED** Production sensitive only | **INFERRED** Active token is configured, because the code's empty-token path returns `503`. |
| `MDC_PROVIDER_LIFECYCLE_ACTOR_REQUIRED`, `MDC_PROVIDER_CONCURRENCY_REQUIRED` | **VERIFIED** Explicit entries for both targets | **NOT VERIFIED** Current write enforcement. The source defaults are both `True`. |
| `MDC_PROVIDER_PUBLICATION_ENABLED`, `MDC_PROVIDER_VALIDATION_ENABLED` | **VERIFIED** Explicit entries for both targets | **NOT VERIFIED** Current values behind lifecycle auth. Production defaults are both `False`. The prior P3.2 Stage B profile explicitly enabled them. |

**VERIFIED** A valid `x-vercel-protection-bypass` header, where authorized and configured, is evaluated by Vercel at its edge. Django evaluates `Authorization: Bearer …` inside the lifecycle handler. A credential for either layer grants access only at that layer. The audit requests used neither credential. [Vercel Protection Bypass for Automation](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation)

- **VERIFIED** Setting `MDC_PROVIDER_LIFECYCLE_AUTH_REQUIRED=False` in a new deployment removes the Django token requirement across the affected routes. Lifecycle GET then reaches the database lookup, which can return `200` or `404`. Validation can reach the validation flag and payload checks. Writes still depend on publication, data readiness, and their remaining guards.
- **VERIFIED** `MDC_PROVIDER_LIFECYCLE_ACTOR_REQUIRED` applies to writes only. If enabled, missing `X-MDC-Actor-Id` produces `400 actor_attribution_required`. If disabled, callers can omit it. An invalid supplied value can still produce `400`. Actor attribution does not confer permission.
- **VERIFIED** `MDC_PROVIDER_CONCURRENCY_REQUIRED=True` requires a current strong ETag on PATCH. In accepted code, DELETE requires it regardless of the flag. Missing yields `428`, malformed or conflicting input yields `400`, and a stale token yields `412`. Use the resource's latest detail ETag. `If-Match` is canonical. `X-MDC-If-Match` accepts the same value on Vercel when intermediary conditional handling could report a false `412` after commit. The read-only routes already serving `200` have no lifecycle Bearer requirement. ## 8. Root Cause of Current 401 Responses

1. **VERIFIED** `GET /api/providers/{provider_id}`, the offering list and detail GETs, and publication validation reach Django on the public Production alias. Their responses include contract `1.0` and `error.code=trusted_lifecycle_auth_required`. The response challenges with Bearer.
2. **VERIFIED** The deployed handlers call `authenticate_lifecycle_request` before provider/offering lookup or the validation/publication switches. With effective `MDC_PROVIDER_LIFECYCLE_AUTH_REQUIRED=True` and a configured service token, a request without valid MDC Bearer authentication returns that exact `401`. This accounts for the same response on disposable nonexistent IDs. Database availability, an actor header, and an ETag are irrelevant to that GET decision.
3. **VERIFIED** Production has an explicit auth flag entry, created before the active deployment. **INFERRED** The configured entry is the source of the active `True` value. The code also defaults to `True`, so deleting the entry would preserve the requirement under Production settings. The exact deployed configuration snapshot was not inspected.
4. **VERIFIED** The stable alias reaches Django without Vercel credentials. Other hosts tested reject the same unauthenticated health call at Vercel's protection layer. Changing the MDC flag does not change Vercel's protection scope.

## 10. Security and Operational Risks

- **VERIFIED** The stable Production alias accepts unauthenticated requests. The two MDC switches remove the app-level Bearer and actor requirements when disabled. **INFERRED** Enabling writes with those switches off on the open alias would grant Internet callers the ability to create, change, or delete operational records. This is unacceptable for the pilot. Treat Vercel protection or controlled Marketplace ingress as the access boundary and verify it before enabling lifecycle access. [Vercel WAF rule configuration](https://vercel.com/docs/vercel-firewall/vercel-waf/rule-configuration)
- **VERIFIED** ETags prevent stale writes, and lifecycle GET returns an ETag to any caller admitted to the handler. ETags cannot authenticate callers. Keep the concurrency setting on, and cover lifecycle GETs in the same access review because they expose operational catalogue data.
- **VERIFIED** Accepted DELETE is a hard operational delete. A database backup or point-in-time recovery is needed for inadvertent changes. A deployment rollback only selects application code and its environment snapshot.
- **VERIFIED** Full-graph publication has a larger data impact than a single lifecycle write. Keep the semantic switches off while the Graph Store and source database are unverified. Enabling automatic mode can also replace a working fallback search with `503` if the authoritative graph is stale or unreachable.
- **INFERRED** Manual deploys reproducibly serve the accepted backend only when the exact Git SHA, app root, environment target, migration state, and Postman evidence are recorded. An older `READY` Preview can still reference removed infrastructure or differ from current settings.

3. **Reconcile PostgreSQL independently.** A code rollback keeps schema and row changes. Retain additive schema unless the operator has a reviewed compatibility or restoration plan. Reconcile changes by provider, offering, and publication ID, using the recorded restore point or an approved targeted restoration. Preserve queued publication history. Re-run the migration compatibility check before restoring an older writer.
4. **Reconcile Fuseki if a separate semantic rollout wrote to it.** Disable further graph replacement first. Restore from a verified snapshot only after confirming the database and graph are on the intended revision. Compare the query-visible revision before re-enabling recovery.
